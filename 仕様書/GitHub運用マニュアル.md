# Unity Git 運用マニュアル（詳細解説版）

## はじめに：チーム開発とGitについて

**チーム開発**とは、複数の開発者が同じプロジェクトを同時に作業することです。**Git**は、そのような開発で「誰が」「いつ」「何を」変更したかを記録・管理するツールです。

**なぜGitが必要？**
- 複数人が同じファイルを編集しても、変更を統合できる
- 過去の任意の時点に戻ることができる
- 誰がどの変更を加えたかが分かる
- バックアップとしても機能する

## 1. ブランチ戦略

### Git Flow ベースの運用

**ブランチ**とは、開発作業を分岐させるための仕組みです。本のページのように、同じプロジェクトから複数の「作業版」を作ることができます。

```
main (master)     ← 完成品が置かれる場所（お客様に提供するバージョン）
├── develop       ← 開発チームの作業場所（開発中のバージョンを統合）
│   ├── feature/player-movement    ← 個人の作業場所（プレイヤー移動機能を開発）
│   ├── feature/enemy-ai          ← 個人の作業場所（敵のAI機能を開発）
│   └── feature/ui-system         ← 個人の作業場所（UI機能を開発）
├── release/v1.0.0               ← リリース準備場所（バグ修正のみ）
├── hotfix/critical-bug-fix      ← 緊急修正場所（重大なバグを即座に修正）
└── support/v0.9.x               ← 古いバージョンのサポート場所
```

#### ブランチの役割（詳細説明）

- **main**: 
  - 役割：その時点の完成版
  - いつ触る：リリース時、ドキュメント更新時、機能統合時

- **feature/**: 
  - 役割：個人が新機能を開発する場所
  - 誰が触る：担当開発者
  - いつ触る：新機能開発中
  - 例：「プレイヤーのジャンプ機能だけ」を開発

- **release/**: 
  - 役割：リリース前の最終チェック・調整
  - 誰が触る：リーダーとテスター
  - いつ触る：リリース直前
  - 例：「バージョン1.0をリリースする前の最終調整」

- **hotfix/**: 
  - 役割：緊急のバグ修正
  - 誰が触る：指定された開発者
  - いつ触る：重大なバグが発見された時
  - 例：「ゲームがクラッシュする致命的バグ」の修正

- **support/**: 
  - 役割：古いバージョンの継続サポート
  - 誰が触る：サポート担当者
  - いつ触る：古いバージョンでバグが発見された時
  - 例：「バージョン0.9のユーザー向けの修正」

### ブランチ命名規則

**命名規則**とは、ブランチの名前をつけるルールです。統一することで、何の作業をしているか一目で分かります。

```bash
# 機能開発（新しい機能を作る時）
feature/[課題番号]-[簡潔な説明]
feature/123-player-inventory    # 課題123番：プレイヤーのインベントリ機能
feature/456-combat-system      # 課題456番：戦闘システム機能

# バグ修正（不具合を直す時）
bugfix/[課題番号]-[簡潔な説明]
bugfix/789-camera-shake-fix    # 課題789番：カメラの揺れ修正

# リリース（版を出す時）
release/v[大].[中].[小]
release/v1.2.0                 # バージョン1.2.0のリリース準備

# ホットフィックス（緊急修正）
hotfix/v[大].[中].[小]
hotfix/v1.1.1                  # バージョン1.1.1の緊急修正
```

**バージョン番号の意味**
- 大（Major）：大幅な変更（例：1.0.0 → 2.0.0）
- 中（Minor）：機能追加（例：1.0.0 → 1.1.0）
- 小（Patch）：バグ修正（例：1.0.0 → 1.0.1）

## 3. コミットルール

### コミットとは？
**コミット**とは、作業の区切りで「この時点の状態を記録する」ことです。ゲームのセーブポイントのようなものです。

### コミットメッセージ形式

**コミットメッセージ**は、「何を変更したか」を他の人に伝える説明文です。

```
[種類](範囲): 件名（何をしたか）

詳細説明（なぜ、どのように）

関連情報
```

#### 例：
```
feat(player): プレイヤーのジャンプアクション実装

- ジャンプの高さを設定可能に    ← 何を追加したか
- 二段ジャンプ機能を追加        ← 何を追加したか  
- アニメーション連携を実装      ← 何を追加したか

Closes #123                     ← 関連する課題番号
```

### コミットタイプ（変更の種類）

- **feat**: 新機能（feature = 機能）
  - 例：「新しいキャラクターを追加」
- **fix**: バグ修正
  - 例：「プレイヤーが壁をすり抜ける不具合を修正」
- **docs**: ドキュメント更新（documentation = 文書）
  - 例：「操作方法の説明書を更新」
- **style**: コードスタイル修正
  - 例：「インデント（字下げ）を統一」
- **refactor**: リファクタリング（機能は同じでコードを整理）
  - 例：「同じ処理をまとめて効率化」
- **perf**: パフォーマンス改善（performance = 性能）
  - 例：「ゲームの動作を軽くする」
- **test**: テスト追加・修正
  - 例：「新機能が正しく動くかのチェックを追加」
- **chore**: その他の作業（雑務）
  - 例：「設定ファイルの更新」
- **asset**: アセット追加・更新
  - 例：「新しい3Dモデルを追加」

### スコープ例（どの部分の変更か）

- **player**: プレイヤー関連
- **enemy**: 敵キャラクター関連  
- **ui**: UI（ユーザーインターフェース）関連
- **audio**: オーディオ（音）関連
- **scene**: シーン（場面）関連
- **system**: システム（全体に関わる）関連
- **doc**:ドキュメントや資料関連

## 4. アセット管理

### アセットとは？
**アセット**とは、ゲームで使用するファイルの総称です。3Dモデル、画像、音楽、動画などが含まれます。

### アセット追加時の注意点

**Unityの.metaファイル**について：
Unityは、すべてのアセットに対して「.meta」という設定ファイルを自動生成します。これは「このファイルがどんな設定か」を記録するものです。

```bash
# アセット追加の流れ
1. Unity でアセットをインポート        ← ファイルをUnityプロジェクトに取り込む
2. .meta ファイルが生成されることを確認  ← Unityが自動で設定ファイルを作成
3. git add でアセットと .meta を同時に追加  ← 両方セットでGitに登録
4. コミット前に Unity でプロジェクトを保存  ← 設定を確定する

# 正しい追加方法（アセットと設定ファイルは必ずセット）
git add Assets/Models/Player.fbx        # 3Dモデル本体
git add Assets/Models/Player.fbx.meta   # 3Dモデルの設定ファイル
```

**重要：.metaファイルを忘れると**
- 他の開発者のUnityプロジェクトで設定が崩れる
- アセットの参照が切れて、ゲームが正しく動かない
- チーム全体に迷惑をかける

### アセット削除時の注意

```bash
# Unity エディターでアセット削除    ← Unityの画面上でファイルを削除
# 対応する .meta ファイルも自動削除される  ← Unityが自動で設定ファイルも削除
# Git でも削除を反映              ← Gitにも削除を伝える
git add -A  # 削除も含めてステージング（削除もGitの変更として記録）
```

## 5. シーン・プレハブ管理

### Unity用語説明
- **シーン**：ゲームの1画面分（タイトル画面、ゲーム画面、設定画面など）
- **プレハブ**：再利用可能なオブジェクトのひな型（敵キャラクター、アイテムなど）

### シーン作業のルール

**シーンファイルは特に注意が必要**：
- 複数人が同じシーンを編集すると競合（コンフリクト）しやすい
- シーンファイルは1つの大きなファイルなので、部分的な統合が困難
- 事前の調整とルールが重要

1. **作業前確認**
   ```bash
   # 最新のdevelopブランチに同期（他の人の最新作業を取得）
   git checkout develop
   git pull origin develop
   
   # 新しいブランチ作成（自分専用の作業場所を作成）
   git checkout -b feature/123-level-design
   ```

2. **シーン保存ルール**
   - シーン変更後は必ず Unity で保存 ← **忘れやすいが重要**
   - `Ctrl+S` でシーン保存 ← 現在のシーンのみ保存
   - `Ctrl+Shift+S` でプロジェクト全体保存 ← すべての変更を保存

3. **コミット前チェックリスト**
   - [ ] シーンが保存されている ← 未保存だとGitに反映されない
   - [ ] コンソールエラーがない ← エラーがあると他の人も困る
   - [ ] プレイテストが正常動作する ← 基本動作の確認

### プレハブの競合回避

**プレハブ競合の問題**：
複数人が同じプレハブを同時に編集すると、設定が混在して壊れる可能性があります。

```bash
# プレハブ変更時のルール
1. プレハブ編集前にブランチ確認     ← 正しい作業ブランチにいるか確認
2. 他の人が同じプレハブを編集していないか確認  ← チームに声かけ
3. 小さな変更単位でコミット       ← 大きな変更は競合リスクが高い
4. プレハブのネスト構造を避ける    ← 複雑な構造は競合時の解決が困難
```

## 6. マージ・プルリクエスト

### 用語説明
- **マージ**：複数のブランチの変更を統合すること
- **プルリクエスト**：「自分の変更をメインブランチに取り込んでください」という依頼

### プルリクエスト作成前

**なぜrebaseが必要？**
他の人の変更で、developブランチが更新されている可能性があります。自分の変更を統合する前に、最新の状態に合わせる必要があります。

```bash
# developブランチとの同期
git checkout feature/123-player-movement  # 自分の作業ブランチに移動
git fetch origin                          # リモートの最新情報を取得
git rebase origin/develop                 # developの最新変更を自分のブランチに反映

# コンフリクト解決後
git push --force-with-lease origin feature/123-player-movement
```

### プルリクエストテンプレート

**プルリクエスト**では、何を変更したかを詳しく説明します。レビューする人が理解しやすくするためです。

```markdown
## 変更内容
- [ ] 新機能追加
- [ ] バグ修正
- [ ] リファクタリング
- [ ] アセット更新

## 概要
[変更内容の詳細説明]
例：プレイヤーキャラクターにジャンプ機能を追加しました。
    ジャンプの高さは設定で調整可能で、二段ジャンプにも対応しています。

## テスト項目
- [ ] ビルドエラーなし              ← ゲームが正常にビルドできるか
- [ ] 既存機能への影響なし          ← 他の機能が壊れていないか
- [ ] パフォーマンステスト完了      ← ゲームの動作が重くなっていないか
- [ ] デバイステスト完了（該当する場合） ← 実機での動作確認

## スクリーンショット・動画
[必要に応じて添付]
例：新機能の動作画面のスクリーンショットや動画

## 関連Issue
Closes #123  ← この変更で解決される課題の番号
```

### レビューポイント

**コードレビュー**とは、他の開発者が変更内容をチェックすることです。品質向上とバグ防止が目的です。

1. **コード品質**
   - コーディング規約遵守 ← チーム内のルールに従っているか
   - パフォーマンス考慮 ← ゲームの動作が重くならないか
   - 適切なコメント ← 他の人が理解できるコメントがあるか

2. **Unity固有**
   - シリアライズ設定確認 ← Unityの設定が適切か
   - アセット参照の妥当性 ← ファイルの参照が正しいか
   - シーン設定の確認 ← シーンの設定が適切か

3. **プロジェクト影響**
   - 既存機能への影響 ← 他の機能に悪影響がないか
   - ビルドサイズへの影響 ← ゲームファイルサイズが大きくなりすぎないか
   - パフォーマンスへの影響 ← ゲームの動作速度に問題ないか

## 7. コンフリクト解決

### コンフリクト（競合）とは？
**コンフリクト**は、複数の人が同じファイルの同じ部分を異なる内容で変更した時に発生します。Gitが「どちらが正しいか判断できない」状態です。

### Unity YAML マージ

**YAML**は、Unityが設定を保存する形式です。人間には読みづらいですが、Unityが自動で管理しています。

```bash
# Unity SmartMerge使用（Unityが提供する専用ツール）
git mergetool --tool=unityyamlmerge [conflicted-file]

# 手動マージが必要な場合
1. コンフリクトファイルを Unity で開く    ← Unityエディターで開く
2. 適切な設定に手動調整              ← 正しい設定に修正
3. ファイル保存後にマージ完了          ← Unity上で保存してGitに反映
```

### シーンコンフリクト対応

**シーンファイルでのコンフリクト**は最も解決が困難です。シーン全体の設定が含まれるため、慎重な対応が必要です。

```bash
# シーンファイルでコンフリクトが発生した場合
1. コンフリクトしたシーンを Unity で開く   ← Unityでシーンを開く
2. 必要なオブジェクトを手動で再配置      ← 正しい配置に調整
3. シーンを保存                      ← Unityで保存
4. git add でコンフリクト解決をマーク    ← Gitに解決完了を通知
```

**予防策**：
- 同じシーンを同時に編集しない
- 小さな変更を頻繁にコミット
- 作業前にチーム内で調整

## 8. デイリー運用

### 作業開始時（毎日の始業時）

```bash
# 1. develop ブランチを最新に更新（他の人の最新作業を取得）
git checkout develop
git pull origin develop

# 2. 機能ブランチ作成（今日の作業用ブランチを作成）
git checkout -b feature/456-new-feature

# 3. Unity プロジェクト開き直し
# プロジェクトを Unity で開き直して設定を同期
```

**なぜ毎日これが必要？**
- 他の開発者が昨日追加した変更を取得するため
- 古い状態で作業すると、後でコンフリクトが発生しやすい
- チーム全体で最新の状態を共有するため

### 作業終了時

```bash
# 1. Unity プロジェクト保存（**最重要**）
# Ctrl+Shift+S でプロジェクト全体保存

# 2. 変更確認（何を変更したか確認）
git status    # 変更されたファイル一覧
git diff      # 変更内容の詳細

# 3. ステージング（Gitに登録する変更を選択）
git add .     # すべての変更をステージング

# 4. コミット（変更を記録）
git commit -m "feat(player): ジャンプ機能を実装"

# 5. プッシュ（サーバーに変更を送信）
git push origin feature/456-new-feature
```

**なぜ毎日終了時にこれが必要？**
- 作業の成果を記録・バックアップするため
- 他の開発者が翌日に最新状態を取得できるようにするため
- PCトラブル等で作業が失われることを防ぐため

### 定期的なメンテナンス

```bash
# 週次作業
1. 不要なブランチ削除（完了した作業ブランチの掃除）
   git branch -d feature/completed-feature
   
2. LFS容量確認（大きなファイルの使用量チェック）
   git lfs ls-files --size
   
3. .gitignore 更新確認（除外ファイル設定の確認）
   新しいUnityバージョンでの除外項目確認
```

## 9. トラブルシューティング

### よくある問題と対処法

#### Library フォルダがコミットされた場合

**Libraryフォルダ**は、Unityが自動生成する一時ファイルです。容量が大きく、環境依存なので、Gitで管理してはいけません。

```bash
# Library フォルダを履歴から削除
git rm -r --cached Library/                    # Gitの管理から除外
git commit -m "chore: Library フォルダを除外"    # 除外をコミット
```

#### .meta ファイルが不整合

**.metaファイルの不整合**は、アセットの設定が壊れた状態です。Unityで再インポートすると修復されます。

```bash
# Unity でアセットを再インポート
1. Assets > Reimport All              # すべてのアセットを再インポート
2. 生成された .meta ファイルをコミット  # 修復された設定ファイルを保存
```

#### LFS容量制限

**LFS容量制限**に達すると、大きなファイルをプッシュできなくなります。

```bash
# 大きなファイルの特定（どのファイルが容量を使っているか確認）
git lfs ls-files --size | sort -k2 -nr

# 古いLFSファイルの削除（不要になった古いファイルを削除）
git lfs prune --verify-remote
```

#### Unity バージョン不整合

**Unityバージョン不整合**は、チームメンバーが異なるUnityバージョンを使っている状態です。互換性問題が発生します。

```bash
# プロジェクトバージョン確認
cat ProjectSettings/ProjectVersion.txt

# チーム内でUnityバージョン統一を確認
例：全員が Unity 2023.3.0f1 を使用することを確認
```

### 緊急時対応

#### 間違ったコミットの取り消し

**コミットの取り消し**は慎重に行う必要があります。特に、すでにプッシュした変更は他の人に影響する可能性があります。

```bash
# 直前のコミットを取り消し（ローカルのみ、まだプッシュしていない場合）
git reset --soft HEAD~1

# プッシュ済みコミットの取り消し（安全な方法）
git revert [commit-hash]    # 取り消し用の新しいコミットを作成
```

#### 破損したリポジトリの復旧

**リポジトリの破損**は、Gitの管理データが壊れた状態です。最後の手段として、新しくクローンし直します。

```bash
# 新しくクローン作成（サーバーから最新状態をダウンロード）
git clone [repository-url] project-backup
cd project-backup

# 作業中のファイルを手動でコピー（未保存の作業があれば手動で移行）
# Unity プロジェクトを開いて整合性確認（正常に開けるか確認）
```

## 10. セキュリティとベストプラクティス

### 機密情報の除外

**機密情報**（APIキー、パスワードなど）をGitに含めてはいけません。一度コミットすると、履歴に残り続けます。

```gitignore
# API キーやパスワードを含むファイル
Assets/Resources/Config/              # 設定フォルダ全体を除外
Assets/StreamingAssets/config.json   # 設定ファイルを除外
Assets/Scripts/Config/ApiKeys.cs     # APIキーファイルを除外

# プラットフォーム固有の設定
Assets/Plugins/Android/AndroidManifest.xml  # Android設定
Assets/Plugins/iOS/Info.plist               # iOS設定
```

### 大容量ファイル対策

**大容量ファイル**は、Git操作を遅くし、容量制限にも影響します。

- 100MB超えるファイルはGit LFS必須 ← Gitの制限
- テクスチャは適切な解像度に最適化 ← 4K画像は本当に必要？
- 音声ファイルは圧縮形式を使用 ← WAVよりもOGGやMP3
- 動画ファイルは外部ストレージ検討 ← YouTube等の外部サービス利用

### チーム間コミュニケーション

**コミュニケーション**はチーム開発の成功に不可欠です。技術的な問題の多くは、事前の相談で回避できます。

- 大きなアセット追加前にチーム通知 ← 容量への影響を事前共有
- シーン編集の衝突を避けるため事前調整 ← 「今日はタイトルシーンを編集します」
- リファクタリング前に影響範囲を共有 ← 「プレイヤークラスを大幅変更します」
- コードレビューは24時間以内に実施 ← 遅れると作業が止まる

## まとめ：成功するチーム開発のために

1. **ルールを守る**：面倒に感じても、ルールがあることで大きなトラブルを避けられます
2. **コミュニケーションを大切に**：技術的な問題の多くは、事前の相談で解決できます
3. **小さく、頻繁に**：大きな変更より、小さな変更を頻繁にコミットする方が安全です
4. **分からないことは聞く**：Gitの操作で迷ったら、必ず先輩や同僚に確認しましょう

この運用マニュアルに従うことで、Unityプロジェクトでの効率的なチーム開発が可能になります。
